# بازیابی یک کارگاه

> برای وقتی که **یک** کارگاه داده‌اش را از دست داده و بقیه سالم‌اند. اگر کل
> دیتابیس رفته، `restore-database.md` را بخوان — این سند برای آن نیست.
>
> این یک روال دستی و پشتیبانی‌محور است، نه یک ویژگی در اپ. جایگزین کردن
> ردیف‌های یک مستأجر در اسکیمای مشترک در حالی که بقیه زنده‌اند، آن‌قدر خطرناک
> است که نباید پشت یک دکمه باشد.

## آنچه باید از اول بدانی

**کارگاه با شناسه‌ی تازه برمی‌گردد، نه شناسه‌ی قبلی‌اش.** شناسه‌ها از
sequenceهای مشترک بین همه‌ی مستأجرها می‌آیند، پس برگرداندن شناسه‌های قدیمی با
ردیف‌هایی که کارگاه‌های دیگر در این فاصله ساخته‌اند تداخل می‌کند.

**پیامدش:** کاربران آن کارگاه باید دوباره وارد شوند. توکن‌های قبلی‌شان به
شناسه‌ی قدیمی اشاره می‌کنند و کار نمی‌کنند. این را از قبل به مشتری بگو.

**عکس‌ها دست‌نخورده می‌مانند.** روی ArvanCloud هستند و ستون `filepath` کلید
کامل شیء را نگه می‌دارد، پس بعد از بازیابی خودبه‌خود نمایش داده می‌شوند —
حتی با اینکه کلیدشان پیشوند کارگاه قدیمی را دارد.

⚠️ عارضه‌اش این است که اشیای این کارگاه زیر پیشوند قدیمی می‌مانند. اگر روزی
خواستی «همه‌ی اشیای کارگاه X را پاک کن»، پیشوند به‌تنهایی کافی نیست.

## ۱. استخراج

```bash
# کلید خصوصی را موقتاً بگذار
cat > /tmp/age-key.txt << 'EOF'
<کل محتوای کلید از password manager>
EOF
chmod 600 /tmp/age-key.txt

./ops/extract-workspace.sh <backup.age> <شناسه-کارگاه> /tmp/age-key.txt
```

اگر شناسه‌ی کارگاه را نمی‌دانی، از بکاپ پیدایش کن — اسکریپت نام کارگاه را
چاپ می‌کند، پس با چند بار امتحان کردن هم می‌شود.

خروجی یک فایل `workspace-<id>-<timestamp>.sql` است.

⚠️ آن فایل داده‌ی خام مشتری است. در گیت نرود و بعد از کار پاکش کن.

## ۲. بررسی تداخل شماره تلفن — این قدم را رد نکن

نام کاربری در کل پلتفرم یکتاست. اگر صاحب کارگاه بعد از حادثه دوباره ثبت‌نام
کرده باشد — که کار طبیعی هر آدم مستأصلی است — بارگذاری وسط کار شکست می‌خورد.

شماره‌های داخل فایل را دربیاور:

```bash
sed -n '/^COPY public.users/,/^\\\.$/p' workspace-*.sql \
  | tail -n +2 | head -n -1 | awk -F'\t' '{print $4}'
```

بعد ببین کدامشان در دیتابیس زنده هست:

```bash
docker compose exec postgres psql -U dofixo -d <دیتابیس> -c "
  SELECT u.username, u.workspace_id, w.name, u.created_at
  FROM users u JOIN workspaces w ON w.id = u.workspace_id
  WHERE u.username IN ('<شماره۱>', '<شماره۲>');"
```

**اگر خروجی خالی بود،** برو به قدم ۳.

**اگر ردیفی برگشت،** تصمیم با توست و باید با مشتری هماهنگ شود:

- **حساب تازه خالی است و کارگاه تازه‌اش بی‌مصرف؟** آن کارگاه را حذف کن
  (`DELETE FROM workspaces WHERE id = <شناسه>` — بقیه cascade می‌شود)، بعد
  بارگذاری کن.
- **حساب تازه داده‌ی جدید دارد؟** حالا دو مجموعه داده داری و ادغامشان کار
  دستی است. با مشتری صحبت کن که کدام را می‌خواهد.

⚠️ هرگز شماره را در فایل بازیابی خودکار تغییر نده. حسابی که کسی نمی‌تواند
واردش شود، از نبودنش بدتر است — چون کاربر فکر می‌کند داده‌اش برگشته.

## ۳. بارگذاری

**کل کار در یک تراکنش.** بارگذاری نیمه‌کاره از هر چیزی بدتر است — ردیف‌هایی
باقی می‌مانند که به ردیف‌های ناموجود اشاره می‌کنند.

```bash
{ echo "BEGIN;"; cat workspace-*.sql; echo "COMMIT;"; } \
  | docker compose exec -T postgres psql -U dofixo -d <دیتابیس> \
      -v ON_ERROR_STOP=1
```

`ON_ERROR_STOP=1` مهم است: بدون آن، psql بعد از خطا ادامه می‌دهد و
`COMMIT` را هم اجرا می‌کند.

اگر شکست خورد، هیچ‌چیز نوشته نشده. خطا را بخوان و از قدم ۲ دوباره شروع کن.

## ۴. جلو بردن sequenceها — فراموش نکن

docker compose exec postgres psql -U dofixo -d <دیتابیس> -t -c "
SELECT format(
'SELECT setval(%L, GREATEST((SELECT COALESCE(max(id),0) FROM public.%I), 1));',
s.sequencename,
replace(s.sequencename, '\_id_seq', ''))
FROM pg_sequences s
WHERE s.schemaname = 'public'
AND s.sequencename LIKE '%\_id_seq';" \
 | docker compose exec -T postgres psql -U dofixo -d <دیتابیس>

⚠️ از `pg_sequences` می‌آید نه `information_schema.tables` یا
`pg_get_serial_sequence`. آن دو روی جدول‌های سیستمی می‌شکنند، چون Postgres
ترتیب ارزیابی شرط‌های `WHERE` را تضمین نمی‌کند و تابع ممکن است قبل از فیلتر
schema اجرا شود. این نسخه به قرارداد نام‌گذاری `<جدول>_id_seq` تکیه می‌کند
که Postgres برای `SERIAL` می‌سازد.

## ۵. تأیید

```bash
docker compose exec postgres psql -U dofixo -d <دیتابیس> -c "
  SELECT w.id, w.name, w.status,
    (SELECT count(*) FROM users u WHERE u.workspace_id = w.id) AS users,
    (SELECT count(*) FROM customers c WHERE c.workspace_id = w.id) AS customers,
    (SELECT count(*) FROM devices d WHERE d.workspace_id = w.id) AS devices
  FROM workspaces w WHERE w.id > 1000000;"
```

بعد **در مرورگر**:

- با حساب آن کارگاه وارد شو (رمزش همان رمز قبلی است — هش بازیابی شده)
- مشتریان، دستگاه‌ها و فاکتورها را ببین
- **یک دستگاه با عکس را باز کن** و مطمئن شو عکس‌ها لود می‌شوند
- ⚠️ **با حساب یک کارگاه دیگر وارد شو و مطمئن شو داده‌ی این یکی را نمی‌بیند**

آخری مهم‌ترین است. اگر ایزولاسیون شکسته باشد، این تنها جایی است که معلوم
می‌شود.

## ۶. پاکسازی

```bash
shred -u /tmp/age-key.txt
rm -f workspace-*.sql /tmp/wsbackup.age
```

## آنچه این روال پوشش نمی‌دهد

**بازیابی جزئی.** «فقط مشتری‌هایی که دیروز پاک شدند» در این سند نیست. کل
کارگاه برمی‌گردد یا هیچ. برای حالت‌های جزئی باید دستی از فایل استخراج‌شده
`INSERT` بنویسی، با احتیاط زیاد.

**ادغام.** اگر کارگاه بعد از حادثه داده‌ی تازه ساخته باشد، این روال آن را
ادغام نمی‌کند — یک کارگاه دوم می‌سازد. ادغام کار دستی است.

**نقطه‌ی زمانی دقیق.** آخرین بکاپ شبانه، آخرین چیزی است که داری. هر کاری که
بعد از آن انجام شده رفته است. این را از اول به مشتری بگو.
