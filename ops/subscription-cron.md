# اجرای شبانه‌ی اشتراک

اسکریپت `subscription-cron.sh` هر شب یک بار اجرا می‌شود و این کارها را می‌کند:

| کار                       | کِی                            |
| ------------------------- | ------------------------------ |
| پیامک «۷ روز مانده»       | ۷ روز مانده به انقضا           |
| پیامک «۱ روز مانده»       | روز آخر                        |
| پیامک «اشتراک تمام شد»    | روز انقضا                      |
| پیامک «دسترسی محدود شد»   | روز سوم بعد از انقضا           |
| پیامک «۷ روز تا حذف»      | روز بیست‌وسوم                  |
| حذف داده                  | روز سی‌ام                      |
| تسویه‌ی پرداخت‌های رهاشده | هر شب، پرداخت‌های هفت روز اخیر |

## نصب

```bash
crontab -e
```

خط زیر را اضافه کن — **ساعت ۲ بامداد به وقت سرور (UTC)**، که حدود ۵:۳۰ صبح
تهران است:

```
0 2 * * * /home/reza/dofixo/subscription-cron.sh >> /home/reza/dofixo-subscription.log 2>&1
```

⚠️ **بعد از بکاپ، نه قبلش.** بکاپ ساعت ۱ اجرا می‌شود؛ اگر این جلوتر باشد،
شبی که کارگاهی حذف می‌شود آخرین بکاپ قبل از حذف گرفته نشده است.

⚠️ اسکریپت `BACKEND_SERVICE` را از `ops/backup.env` می‌خواند. اگر نباشد،
`backend` فرض می‌شود.

## بررسی

```bash
cat ~/dofixo-subscription.log
```

خط پایانی هر اجرا این شکل است:

```
subscription job: notified=2 status=1 deleted=0 settled=0 failures=0 (3s)
```

⚠️ **`failures` بزرگ‌تر از صفر یعنی یک کارگاه رد شد، نه اینکه کل اجرا شکست
خورد.** بقیه‌ی کارگاه‌ها انجام شده‌اند. دلیلش بالای همان لاگ نوشته شده.

## اجرای دستی

```bash
cd ~/dofixo && ./subscription-cron.sh
```

بی‌خطر است: هر پیامکی که فرستاده شده در `subscription_notifications` ثبت است
و دوباره فرستاده نمی‌شود.

## اگر پیامک‌ها نمی‌روند

۱. **`HTTP 401` در لاگ** → IP سرور از پنل sms.ir افتاده. با
`curl -s https://api.ipify.org` آدرس فعلی را بگیر و ثبتش کن.

۲. **`HTTP 400`** → شناسه‌ی قالب اشتباه است، معمولاً قالب sandbox در
`.env.prod`. پنج متغیر `SMS_TEMPLATE_*` را چک کن:

```
SMS_TEMPLATE_BEFORE_EXPIRY=398956
SMS_TEMPLATE_ON_EXPIRY=764207
SMS_TEMPLATE_AFTER_EXPIRY=450597
SMS_TEMPLATE_PAYMENT_OK=344895
SMS_TEMPLATE_REFERRAL_REWARD=549585
```

۳. **`status 115`** → آن شماره در فهرست سیاه sms.ir است. مال یک کارگاه است،
نه مشکل ما.

۴. **`has no active super admin`** → کارگاه سوپرادمین فعالی ندارد. پیامک فقط
به او می‌رود، چون پول از جیب او می‌رود.

## اگر حذف انجام نشد

حذف داده در یک تراکنش است، پس یا کامل انجام شده یا اصلاً نه. اجرای دوباره‌ی
اسکریپت دوباره تلاش می‌کند.

⚠️ **ردیف کارگاه هرگز حذف نمی‌شود** — سنگ قبرش با `deleted_at` می‌ماند، چون
`payments` به آن اشاره دارد و دفتری که موضوعش ناپدید شود دفتر نیست.

```sql
SELECT id, name, deleted_at FROM workspaces WHERE deleted_at IS NOT NULL;
```

⚠️ حذف عکس‌ها روی آروان اگر شکست بخورد، **لاگ می‌شود ولی حذف ردیف‌ها را متوقف
نمی‌کند**. یک شیء یتیم چند کیلوبایت هدر می‌دهد؛ خطای پرتاب‌شده کارگاهی جا
می‌گذارد که هیچ‌کس نمی‌تواند حذفش را تمام کند.

## پرداخت‌های رهاشده

پرداختی که پولش کم شده ولی کاربر به صفحه‌ی بازگشت نرسیده، در وضعیت `paid`
می‌ماند. این اسکریپت هر شب پرداخت‌های **هفت روز اخیر** را از زیبال استعلام
می‌کند و آن‌هایی را که واقعاً پرداخت شده‌اند تمدید می‌کند.

⚠️ **قدیمی‌تر از هفت روز دنبال نمی‌شود.** کوئری‌ای که تا ابد عقب برود بزرگ‌تر
و بزرگ‌تر می‌شود، و مشتری‌ای که سه هفته پیش منصرف شده نباید ناگهان اشتراک
فعال ببیند.

اگر کسی تماس گرفت که «پول دادم ولی فعال نشد»:

```sql
SELECT id, order_id, track_id, status, amount_rials, created_at
FROM payments WHERE workspace_id = <id> ORDER BY id DESC LIMIT 5;
```

- `pending` → به درگاه نرفته یا برنگشته
- `paid` → پول رفته، تأیید نشده — اسکریپت باید بگیردش
- `verified` → تمدید شده، `subscription_events` را نگاه کن
- `failed` → دلیلش در `failure_reason` است
